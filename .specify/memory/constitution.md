# Robot Control Playground Constitution

상태: 사용자 승인 완료(2026-10-16). 승인된 Constitution과 FK Spec·Plan에 따른 개발 지시를 승인 근거로 기록한다. v1.0.0 원칙 내용은 유지한다.

## Core Principles

### I. Mathematical Correctness

모든 수식과 계산은 변수, 기준 좌표계, 단위, 가정, 적용 조건 및 실패 조건을 명시한다.
2R 평면 로봇은 오른손 좌표계(x 오른쪽, y 위쪽, z 화면 밖)를 사용하며 양의 회전은
반시계 방향이다. theta1은 기준 x축 기준 각도, theta2는 Link 1 기준 상대 각도이며
기본 단위는 rad, m, s이다. rad를 무차원으로 취급하는 수치 관례는 해당 계산에 명시한다.
링크 길이는 유한한 양수, 목표점과 관절 상태는 유한한 값이어야 한다.
특이점·근접 특이점, 도달 불가능 목표, 경계·퇴화 조건 및 부동소수점 오차를 구분해
처리한다. 기구학적 도달 가능성을 제어기 수렴 보장으로 해석하지 않는다.
이론적 사실, 해석, 가설 및 실제 실험 결과를 구분하고 미확인 결과를 생성하지 않는다.

### II. Spec-Driven Development

기능 구현 전에 상위 요구사항과 연결된 Spec, Plan, Tasks를 작성한다.
Spec에는 검증 가능한 수용 조건과 필수 자동 테스트를 명시하고, Plan에는 수식·단위·구조·
인터페이스·수치 안정성을 구체화하며, Tasks는 요구사항과 구현·테스트 작업을 연결한다.
Spec 검토 후 Plan으로, Plan 검토 후 Tasks로 진행하며, 사용자 검토가 필요한 상태에서는
구현하지 않는다. 자동 생성 산출물도 기준 문서와 대조한다.
기능별 선행 의존성을 명시하고, 실제 설치된 Spec Kit 명령과 경로 해석 방식을 사용한다.

### III. Testing & Reproducibility

pytest 자동 테스트는 필수다. 관련 정상 입력, 경계·특이·퇴화 조건, 도달 불가능 목표 및
비정상 입력을 기능 수용 조건에 따라 검증한다. PROJECT_PLAN.md의 수치 기준을 유지하며
비교 방식과 수치 허용량은 기능 Spec·Plan에서 구체화한다. 실패를 숨기기 위해 테스트를
삭제하거나 수용 기준을 완화하지 않는다.
실행 명령, 환경·의존성 버전, 대상 Commit SHA와 실제 결과·미실행 항목을 기록한다.
실험에는 이름, 모든 사용 파라미터, 초기 상태, 목표점, 단계 수 또는 종료 시간,
최종 위치 오차, 성공·실패 및 종료 사유를 남긴다. 난수를 사용하면 seed를 기록한다.
동일 설정에서 결과를 재현할 수 있어야 하며 실행하지 않은 검증을 통과했다고 보고하지 않는다.

### IV. Minimal Architecture

Python 3.11, NumPy, Matplotlib, pytest 중심의 경량 구조를 유지한다.
Windows 10·RAM 8GB 환경에서 GPU 없이 실행하는 것을 목표로 한다.
기구학·제어·시각화를 분리하고 가능한 한 순수 함수를 사용한다.
입출력 자료형을 명시하고, 실험 파라미터는 한 곳에서 관리하며, OS 독립적인 경로 처리를
사용한다. 새 의존성이나 추상화는 수용 조건에 필요한 근거가 있을 때만 도입한다.
범위와 무관한 대규모 리팩터링 및 관례적인 중복 기준 문서 생성을 하지 않는다.

### V. Independent Verification

Agent A는 승인된 Spec·Plan에 따라 구현·단위 테스트·자체 점검을 수행한다.
Agent B는 초기 역할을 Read-only Reviewer로 유지하며 A와 동일한 기준 문서 및 대상
Commit을 검증한다. B가 직접 수정하는 역할로 전환하려면 사용자에게 범위 승인을 받는다.
A의 테스트만으로 PASS를 선언하지 않고, 가능한 경우 독립 해석 계산, IK→FK 복원,
수치 미분 등 별도 근거를 사용한다. 검증 보고는 대상 SHA, 요구사항, 명령·실제 결과,
결함·미실행 항목·해결 사항 및 PASS/FAIL/BLOCKED 판정을 포함한다.
PR HEAD 변경 시 변경 영향을 확인하고 필요한 검증을 새 Commit에서 다시 수행한다.
가능하면 작업 공간을 분리하며 동일 파일을 동시에 수정하지 않는다.

### VI. Git Traceability

작업 전 로컬 변경과 main·원격 상태를 확인하고 사용자 파일을 보존한다.
기준 브랜치는 main이며 실제 원격 기본 브랜치와 다르면 임의 변경하지 않고 보고한다.
기능별 Branch에서 개발하고 가능한 한 기능 하나를 검토 가능한 PR 하나로 관리한다.
승인된 범위에서 Commit·Push·PR을 수행하고 요구사항, 변경 이유, 테스트 결과,
미해결 사항 및 검증 대상 SHA를 추적한다. main에 임의로 직접 Push하지 않는다.
브랜치 이름과 Spec 디렉터리 이름이 같다고 가정하지 않으며 hook의 Git 부수 효과를
실행 전에 확인한다. CI와 브랜치 보호의 존재를 가정하지 않는다.

### VII. Human Approval

핵심 알고리즘, 프로젝트 범위, 주요 인터페이스 및 수용 기준 변경은 근거·영향·대안을
제시한 뒤 사용자 승인을 받는다. 승인 후 관련 기준 문서·Spec·Plan·Tasks와 코드·테스트를
일관되게 갱신한다. 승인된 범위의 일반적인 구현·수정·자체 점검은 진행한다.
PR Merge는 현재 HEAD의 필수 테스트 통과, B의 필수 검증 PASS, 중요한 미해결 결함 없음,
PR의 변경·검증 기록 및 사용자의 최종 Merge 승인을 모두 충족해야 한다.
자동 수렴 결과와 B의 PASS는 사용자 승인을 대체하지 않는다.

## Project Scope & Constraints

목적은 AI 기반 SDD 개발 워크플로 검증과 2-DOF 로봇 제어 기초 학습이다.
Phase 1은 해석적 FK·IK·Jacobian, Jacobian의 유한차분 비교, DLS 기반 고정 목표점 추종,
Matplotlib 자세·궤적·위치 오차 시각화, 자동 테스트 및 재현 가능한 실험 기록으로 한정한다.
실제 하드웨어, 토크·전체 동역학, 마찰·접촉, 센서 노이즈·상태 추정, MuJoCo,
학습 기반 제어, ROS/ROS 2, 별도 GUI 및 복잡한 분산·클라우드 인프라는 제외한다.
로봇 기본값, 제어 파라미터 및 수치 수용 기준은 PROJECT_PLAN.md를 따른다.
후속 기능의 세부 정책은 승인된 상위 기준을 유지하면서 Spec·Plan에서 결정한다.

## Development Workflow & Quality Gates

작업 시작 시 PROJECT_PLAN.md, AGENTS.md, Constitution, 현재 기능 산출물 및 관련 코드를
실제로 확인한다. 없는 파일이나 공유되지 않은 다른 대화의 결정을 존재한다고 가정하지 않는다.
중요한 작업은 목표·입력·수정 범위·완료 조건·테스트 기준을 명시한다.
Constitution 검토 → Specify → 필요 시 Clarify → Spec 검토 → Plan → Plan 검토 →
Tasks → 필요 시 Analyze → Implement → A의 자체 테스트·PR → B의 독립 검증·재검증 →
사용자 Merge 승인 순서를 따른다. FK, IK, Jacobian, Target Tracking and Visualization의
기능 분리를 권장하며, 세부 인계와 검증 절차는 AGENTS.md를 따른다.
Spec Kit의 기존 스크립트·템플릿·통합을 재사용하고 임의 재설치·초기화·업데이트나
문제 우회를 위한 설정 변경을 하지 않는다. 템플릿의 테스트 선택 안내와 관계없이
이 프로젝트의 자동 테스트는 필수다.

## Governance

PROJECT_PLAN.md는 상위 요구사항, AGENTS.md는 작업 규칙, 승인된 Constitution은 프로젝트
원칙, 기능 Spec은 수용 조건을 정의한다. 문서 간 충돌은 자동 우선순위로 해결하지 않는다.
충돌 위치·영향·대안을 보고하고 사용자 결정을 받은 뒤 승인된 범위에서 정합성을 맞춘다.

최초 채택과 개정은 사용자 검토·승인을 거친다. 개정안에는 이유, 영향받는 원칙·산출물,
필요한 후속 조치 및 버전 변경 근거를 기록한다. 승인 전에는 제안 상태를 명시한다.
버전은 Semantic Versioning을 사용한다. 호환되지 않는 원칙 삭제·재정의는 MAJOR,
원칙·섹션 추가나 실질적 지침 확장은 MINOR, 의미를 바꾸지 않는 명확화·오탈자는 PATCH다.
최초 정식 버전 제안은 1.0.0이다. 승인일은 실제 최초 채택일로 확정하고 개정일은 실제
문서 수정일로 기록한다. Spec·Plan 검토, 구현 자체 점검 및 B의 검증에서 원칙 준수를
확인한다. 사용자 승인 전에는 다음 기능 명세 단계로 진행하지 않는다.
